# 第二阶段：技术故事评分

评分只看仓库里真实存在的设计。个人贡献一栏一律不超过 3 分：Git 只有一次初始化提交，无法区分设计、实现和生成代码的边界。你若确认某段是自己独立设计和实现的，面试口述可以升到“我做的”，但材料里仍把可证明性保守计分。

## 为什么是这 8 个

这 8 个都能指到具体函数，也能讲出失败场景和替代方案。

下面这些看起来像亮点，但不够单独成故事：

- 拨号盘、主题、检查器布局：业务 UI。
- `CallControls`：按状态渲染按钮，有一个文案测试。
- React/Vue 示例：各一个组件，没有独立状态设计。
- Changesets、tsup、CI：常规工程化，可以放在项目介绍里一句带过。
- 纯函数基准每秒数百万次：没有对照实验，不能当成优化项目。

## 最值得准备的 3 个

1. **本地挂断与晚到接通**。这是通话 SDK 和普通表单提交的差别：两条异步路径会改同一份会话，终态必须不可逆。代码、注释和状态机测试对得上，而且你必须能讲清队列忙、双接通、holding 上的超时这些还没测的洞。
2. **ResourceScope 与销毁**。组件卸载、权限弹窗、信令延迟会叠在一起。现有测试能证明销毁后的计数和晚到事件。你要同时知道“generation”目前并没有换成新 scope。
3. **Headless 端口**。架构深度最高，也最容易被追问穿。准备时把“Core 不依赖框架”和“ConnectionManager / 浏览器媒体 / iframe 还没接上 Core”放在同一段里讲。只讲解耦、不讲未接线，会被认为没看过集成边界。

第 4 名“不自动重放 hangup”面试可展开程度很高，适合作为第 3 名的延伸。不要把它说成 SDK 拨号已经具备的能力。`CloudCallSDK.dial` 走的是 `SignalingTransport.send`，Mock 失败会直接抛，根本没有重放队列。重放策略只活在 `ConnectionManager.send`。

## 分数含义

- **复杂度 4**：有真实竞态或分布式语义，但状态空间仍然小，没有会议、咨询转接。
- **架构 5**：依赖方向和端口是整仓的骨架。
- **可证明 2**：实现在，测试几乎没打到这条路径。
- **价值 5**：错了会出现“挂断后仍显示通话中”或重复外呼这一类用户能感知的错误。当前没有线上数据，所以价值是推断的严重性，不是已度量的收益。
- **可展开 5**：能连续往下讲边界、复杂度和替代方案，而且这些分支在代码里找得到。
